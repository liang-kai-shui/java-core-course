1. main都返回了，窗口为什么还在

你在终端运行一个窗口程序，最后一行 main 早就执行完了，PowerShell 却没有回到提示符；窗口还能拖动、还能关闭，关掉之后命令才结束。这与前面所有控制台程序都不一样：那些程序 main 一返回，进程就退出了。

先把两件事分开：main 是主线程的入口，它返回只表示这条线程执行完了；窗口程序启动后，Swing 还会使用一条界面事件线程（事件分派线程，EDT）和与窗口系统打交道的线程。只要还有可显示的顶层窗口，这些线程就还在工作，进程就不会结束。像餐厅里点完菜：接待你的服务员（main）下班了，厨房和前台（EDT）还在营业；最后一位顾客（窗口）离开，店才打烊。类比边界是：main 不是"转到后台继续跑"，它确实结束了；Swing 也不是靠一个"窗口计数变量"决定退出，而是由窗口系统与 AWT 的自动结束机制决定。

import java.awt.Dimension;
import java.awt.EventQueue;
import javax.swing.JFrame;
import javax.swing.JPanel;

public class MinimalFrame {
    static JPanel createContent() {
        JPanel panel = new JPanel();
        panel.setPreferredSize(new Dimension(320, 180));
        return panel;
    }

    public static void main(String[] args) throws Exception {
        if (args.length > 0 && args[0].equals("--check")) {
            EventQueue.invokeAndWait(() -> {
                JPanel panel = createContent();
                Dimension preferred = panel.getPreferredSize();
                System.out.println("preferred=" + preferred.width + "x" + preferred.height);
                System.out.println("actual-before=" + panel.getWidth() + "x" + panel.getHeight());
                panel.setSize(360, 200);
                System.out.println("actual-after=" + panel.getWidth() + "x" + panel.getHeight());
            });
            return;
        }
        EventQueue.invokeLater(() -> {
            JFrame frame = new JFrame("Java学习台");
            frame.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
            frame.add(createContent());
            frame.pack();
            frame.setLocationByPlatform(true);
            frame.setVisible(true);
        });
    }
}

应出现一个标题为“Java学习台”的窗口，内容区是空白面板，大约 320×180。注意终端：命令不会立刻结束，要等你关闭窗口。关闭后进程才退出，PowerShell 回到提示符。

时刻 main 线程 EDT 窗口 进程
提交 invokeLater 后 继续走，随即返回 队列里多了一个待执行动作 还没创建 运行中
EDT 执行动作 已结束 new、add、pack、setVisible 出现，可拖动、可关闭 运行中
你点关闭 — 处理关闭事件，按关闭策略退出 消失 结束

EventQueue.invokeLater(() -> {...}) 先把这段代码"排进界面队列"，不保证它已经执行；main 随后就返回了。真正创建窗口的是 EDT，所以打印语句与窗口出现的先后，不能凭源码上下相邻来推断。

只改一处的实验：把 frame.setVisible(true); 改成 frame.dispose();，重新运行。窗口不再出现，命令很快返回——因为窗口被释放，已经没有可显示的顶层窗口了。改回 setVisible(true) 又恢复原现象。

这里有个容易误判的细节：在本机实测，只 pack 而不 setVisible，命令同样不回提示符，因为 pack 已经让窗口进入"可显示"状态。所以决定进程是否继续的，不是"屏幕上有没有像素"，而是"还有没有可显示的顶层窗口"。教材 p408 的说法是：终止 main 只是终止主线程，事件分派线程保持程序激活，直到关闭框架或调用 System.exit。

独立小任务：写一个程序，先打印 main-start，提交一个只打印 queued 的动作，再打印 main-end；把 invokeLater 换成 invokeAndWait 各运行三次，记录两次打印的顺序，说明哪一种能保证顺序。

2. new之后还差三步：关闭策略、尺寸、可见性

new JFrame("Java学习台") 只做了一件事：在堆上创建窗口对象。教材 p408 写得很明确：框架默认大小是 0×0，而且构造后不会自动显示。所以从"有对象"到"能看见"，中间还有三步。

第一步是关闭策略。点右上角关闭按钮时，程序到底做什么，由 setDefaultCloseOperation 决定，默认是"隐藏"，不是退出：

常量 常量值 点关闭后发生什么 典型用途
DO_NOTHING_ON_CLOSE 0 什么都不做，窗口还在 关闭前要弹确认框
HIDE_ON_CLOSE 1 只是把窗口隐藏，对象还在 默认值；多窗口程序
DISPOSE_ON_CLOSE 2 释放这个窗口的本地资源 单窗口，但还想做收尾
EXIT_ON_CLOSE 3 调用 System.exit，整个进程退出 本课这种单窗口小工具

EXIT_ON_CLOSE 最省事，但它等于直接结束进程：别的窗口、后台线程、还没写完的文件都会被一起带走。真实项目里"关一个窗口就全退"往往不是想要的行为，所以这个常量要按需求选，不要当默认写法背下来。

第二步是尺寸。本课用 pack()，它按内容的首选尺寸加上窗口装饰算出外框大小；也可以 setSize(宽, 高) 直接指定外框。两者量的不是同一个东西，下一节展开。

第三步是显示：setVisible(true)。在它之前，你可以从容地 add 组件、设标题、算尺寸，窗口不会闪出来。

语句 这时发生了什么
JFrame frame = new JFrame("Java学习台"); 只有对象：0×0、不可见
frame.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE); 点关闭即退出整个进程
frame.add(createContent()); 把内容放进内容窗格
frame.pack(); 按内容首选尺寸算出外框
frame.setLocationByPlatform(true); 位置交给窗口系统挑
frame.setVisible(true); 这时才真正显示

setLocationByPlatform(true) 要在显示之前调用，交给窗口系统选位置；如果自己 setLocation(x, y)，坐标相对整个屏幕的左上角，而组件内部的坐标相对父容器，这两套坐标在第 12 章还会再分。

顺带说清一个常被问的点：Swing 组件是 Java 自己画出来的，所以能换"观感"（look and feel）。教材 p404–407 讲了 Metal（默认的 Ocean 主题）、Windows/GTK 本地观感，以及 Java 7 起提供、但默认不启用的 Nimbus。书上"JavaFX 将来可能取代 Swing"是写作时代的判断，本课程只按这本书学 Swing，不把它当作今天的桌面技术排名。

独立小任务：把标题改成“我的第一个窗口”，再把 EXIT_ON_CLOSE 换成 HIDE_ON_CLOSE，关闭后观察终端是否回到提示符，解释你看到的现象。

3. 三个不同的数：首选尺寸、当前尺寸、外框尺寸

初学者最常见的困惑是：“我明明设了 320×180，为什么窗口看起来不是这个大小？”因为这里其实有三个数。

.\java.ps1 -Source './L40_第10章A_窗口组件与事件线程/code/MinimalFrame.java' -ProgramArgs @('--check')

--check 不创建顶层窗口，只在 EDT 里检查内容面板，输出三行：

preferred=320x180
actual-before=0x0
actual-after=360x200
数 谁给 量的是什么 本例
首选尺寸 getPreferredSize 内容组件自己算，或你 setPreferredSize 布局建议的内容区大小 320×180
当前尺寸 getSize 布局管理器或 setSize 组件现在的宽高 0×0 → 360×200
外框尺寸 frame.getWidth/getHeight pack/setSize 后由窗口系统算 含标题栏、边框的整扇窗 比内容区大

三行输出的意思是：刚 new 出来的面板还没被布局，实际尺寸是 0×0；setSize(360, 200) 直接改了实际尺寸，但没有改首选尺寸。首选尺寸只是"建议"，pack 采纳它，setSize 则绕过它。

所以 pack() 与 setSize() 的区别不是"一个自动一个手动"，而是：

调用 依据 结果
pack() 内容的首选尺寸 + 窗口装饰 刚好装下内容，窗口可能随内容变化
setSize(w, h) 你给的数 强制外框大小，内容可能被挤压或留白

frame.getWidth() 拿到的是外框宽，包含标题栏和边框，所以 pack 之后它不等于 320；frame.getContentPane().getWidth() 才是内容区宽度。做界面时不要拿外框尺寸去核对内容布局，否则会差出边框那几像素。

只改一处的实验：把 createContent 里的 320, 180 改成 400, 220，先预测 --check 第一行，再运行；最后真实启动，观察窗口是否变大。若你同时改了 setSize 那一行，就无法判断是哪个数在起作用。

独立小任务：不改代码，先用 --check 说明 actual-before 为什么是 0×0；再解释为什么 pack 之后 getWidth() 不等于首选宽度。

4. JFrame不是画布：内容窗格才是放组件的地方

很多人以为 frame.add(...) 是把组件画在"窗口"上。教材 p415 的图 10-8 给出的结构更细：一扇 JFrame 由好几层组成，最外层是框架本身，里面依次是根窗格、层级窗格、可选的菜单栏、内容窗格，最上面还有玻璃窗格。真正承载业务组件的是内容窗格。

import java.awt.EventQueue;
import javax.swing.JRootPane;

public class ContentPaneShape {
    public static void main(String[] args) throws Exception {
        EventQueue.invokeAndWait(() -> {
            JRootPane root = new JRootPane();
            System.out.println("content=" + root.getContentPane().getClass().getSimpleName());
            System.out.println("glass=" + root.getGlassPane().getClass().getSimpleName());
            System.out.println("menu-bar=" + (root.getJMenuBar() == null ? "absent" : "present"));
            System.out.println("layered-children=" + root.getLayeredPane().getComponentCount());
        });
    }
}

输出四行：

content=JPanel
glass=JPanel
menu-bar=absent
layered-children=1

这里没有 new JFrame，只造了一个 JRootPane，因为 JFrame 内部就挂着这样一个根窗格；单独造它，既能看清层次，又不依赖显示环境。layered-children=1 说明内容窗格已经被放进层级窗格，菜单栏默认不存在。

层 类（默认） 职责 本例怎么看
框架 JFrame 顶层窗口，装饰由窗口系统画 不在本程序里
根窗格 JRootPane 把下面几层组装起来 root
层级窗格 JLayeredPane 管理叠放次序（Z 序） layered-children=1
菜单栏（可选） JMenuBar 顶部菜单 menu-bar=absent
内容窗格 Container，默认 JPanel 放业务组件 content=JPanel
玻璃窗格 Component，默认 JPanel 盖在最上层，可拦截输入、画浮层 glass=JPanel

类比：相框（框架）→ 背板（根窗格）→ 分层插槽（层级窗格）→ 画纸（内容窗格）→ 表面玻璃（玻璃窗格）。类比边界是：这些是运行期对象，不是磁盘上嵌套的文件夹，也不是"子类继承父类"的层次；它们之间是包含关系。

教材 p415 还提到一个历史变化：Java SE 1.4 及更早，JFrame.add 会抛异常并提示“用 getContentPane().add”；现在 JFrame.add 只是转交给内容窗格，所以两种写法效果一样。玻璃窗格平时不可见也不拦截鼠标，需要做“整窗遮罩”“拖拽提示层”时才打开它。

只改一处的实验：把 root.getContentPane() 换成 root.getGlassPane() 再打印类名，输出仍是 JPanel，但这不代表两者可以互换——玻璃窗格盖在最上层，用来拦截输入；把业务组件放进去，用户点不到下面的内容。

独立小任务：用自己的话说明 frame.add(button) 究竟把按钮加到了哪一层；如果要求“按钮上方浮一层半透明提示”，应该动哪一层。

5. 组合：容器里装组件，而不是每个窗口都写extends

教材里的示例常用 class SimpleFrame extends JFrame，那是一种写法，但不是唯一写法，也不是本课推荐的默认写法。窗口和内容之间更常见的关系是组合：造一个面板，把组件 add 进去，再把面板交给窗口。像文件柜里放文件夹、文件夹里放纸，而不是"文件夹是一种文件柜"。

import java.awt.BorderLayout;
import java.awt.EventQueue;
import javax.swing.JLabel;
import javax.swing.JPanel;

public class ComponentTreeProbe {
    public static void main(String[] args) throws Exception {
        EventQueue.invokeAndWait(() -> {
            JPanel card = new JPanel(new BorderLayout());
            JPanel body = new JPanel();
            body.add(new JLabel("第一行"));
            card.add(new JLabel("标题"), BorderLayout.NORTH);
            card.add(body, BorderLayout.CENTER);
            System.out.println("card-children=" + card.getComponentCount());
            System.out.println("body-children=" + body.getComponentCount());
            System.out.println("body-in-card=" + (body.getParent() == card));
        });
    }
}

输出三行：card-children=2、body-children=1、body-in-card=true。getComponentCount() 只数直接子组件：card 直接装了标题标签和 body 两块，body 自己装了"第一行"一块，所以分别是 2 和 1；body.getParent() == card 说明 add 建立的是父子关系。

BorderLayout 把容器分成五个区：NORTH、SOUTH、EAST、WEST、CENTER，CENTER 拿走剩余空间。不给位置时默认进 CENTER。同一区再 add 一个组件，后加的会替换先加的，不是并排叠加——这是 L43 布局课的起点，本课只需记住这条规则。

写法 关系 什么时候用
class MyFrame extends JFrame 继承：是一种窗口 需要定制窗口本身的行为
frame.add(panel) 组合：窗口里有一个面板 绝大多数界面组织
panel.add(label) 组合：面板里有一个标签 组件的层层嵌套

extends 让子类获得父类的全部公开能力，也把两者绑死；组合只要求"能放进去"，以后换面板实现不影响窗口。本课的 FirstStudyFrame 用组合：createContent() 返回面板，main 负责窗口，两边各自独立。

只改一处的实验：在 card.add(body, BorderLayout.CENTER) 之后再 card.add(new JLabel("第二行"), BorderLayout.CENTER)，预测 card-children 还是 2，而 body.getParent() 变成 null。运行确认后把这一行删掉。这就是"同一区被替换"的直接证据。

独立小任务：把标题标签改放到 SOUTH，说说组件数变不变、位置变不变；再解释为什么"组件数没变"不能证明布局没变。

6. 界面操作为什么要排队到EDT

Swing 组件不是线程安全的：如果两个线程同时改同一个按钮的文字，可能出现半新半旧的状态。Swing 的约定是——组件的创建、修改、读取，尽量都交给同一条事件分派线程，其它线程只负责"提交一个动作"。

import java.awt.EventQueue;

public class EdtCallSequence {
    public static void main(String[] args) throws Exception {
        System.out.println("before");
        EventQueue.invokeAndWait(() -> System.out.println("edt=" + EventQueue.isDispatchThread()));
        System.out.println("after");
    }
}

输出固定三行：

before
edt=true
after

invokeAndWait 把动作交给 EDT，然后当前线程挂起等待，等动作执行完才继续，所以 after 一定在 edt=true 之后。invokeLater 只负责"排进去"，不等待，main 会立刻往下走，两者先后就不再有保证。实测这条线程的名字是 AWT-EventQueue-0，而且它不是守护线程——所以只要 AWT 还在工作（有可显示的窗口），它就会让进程继续活着。

方法 是否等待 动作在哪执行 用在哪里
invokeLater 不等待 EDT 启动窗口、从后台线程更新界面
invokeAndWait 等待完成 EDT 需要确定顺序的检查、测试

两条禁令要记住：不能在 EDT 里调用 invokeAndWait 等待自己（会抛错，等于自己等自己）；也不能在 EDT 上做耗时工作。后者不是风格问题：EDT 同时负责按钮响应和重绘，你在里面 Thread.sleep 或跑一个长循环，窗口就会"未响应"，拖动、关闭、重绘全部停住。像收银台只有一位收银员，他跑去仓库找货，队伍就全卡住；正确做法是把耗时活交给后台线程，算完再用 invokeLater 把结果送回 EDT（L49、L53 展开）。

只改一处的实验：把 invokeAndWait 换成 invokeLater，运行三次，记录 after 与 edt=true 的先后。你会发现顺序不再由代码保证——这不是 JVM 不稳定，而是你从"等待"换成了"只排队"。

独立小任务：在 main 里打印当前线程名，在动作里再打印一次，对照 main 与 AWT-EventQueue-0；然后说明为什么"界面更新必须在 EDT"不等于"所有计算都必须在 EDT"。

7. 绘制是回调：paintComponent与repaint

窗口第一次出现、被遮挡后露出、被拖动改变大小时，画面都要恢复。如果你只在 main 里画一次，窗口一被遮住，内容就没了。正确做法是把"怎样画当前状态"写进组件的 paintComponent，由 Swing 在需要时回调；你只负责在状态变化后调用 repaint() 请求重画。

import java.awt.Dimension;
import java.awt.EventQueue;
import java.awt.Graphics;
import java.awt.Graphics2D;
import java.awt.image.BufferedImage;
import javax.swing.JFrame;
import javax.swing.JPanel;
public class RepaintFromState {
    static class ReviewPanel extends JPanel {
        private static final long serialVersionUID = 1L;
        private boolean painted;
        @Override public Dimension getPreferredSize() { return new Dimension(200, 100); }
        @Override protected void paintComponent(Graphics g) {
            super.paintComponent(g); painted = true; g.drawString("Study", 20, 50);
        }
    }
    public static void main(String[] args) throws Exception {
        if (args.length > 0 && args[0].equals("--check")) {
            EventQueue.invokeAndWait(() -> {
                ReviewPanel panel = new ReviewPanel(); panel.setSize(200, 100);
                BufferedImage image = new BufferedImage(200, 100, BufferedImage.TYPE_INT_RGB);
                Graphics2D g = image.createGraphics();
                try { panel.printAll(g); } finally { g.dispose(); }
                System.out.println("painted=" + panel.painted);
            });
        } else EventQueue.invokeLater(() -> {
            JFrame frame = new JFrame("绘制状态"); frame.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
            frame.add(new ReviewPanel()); frame.pack(); frame.setLocationByPlatform(true); frame.setVisible(true);
        });
    }
}

无参数运行，窗口里显示 Study；加 --check 则把组件画到内存图片上，输出 painted=true。这里 printAll 是离屏检查入口，正常界面刷新用 repaint()，不要手动调用 paintComponent——教材 p416 专门强调了这一点：调用时机由 Swing 决定，你干预只会得到不完整的绘制。

三个细节：

  • super.paintComponent(g) 先让 JPanel 用背景色铺底。不调用它，旧像素可能残留，出现"字叠字"。
  • g.drawString("Study", 20, 50) 的 (20, 50) 是文字基线位置，不是文字框左上角；汉字和字母的基线相同，但视觉高度不同。
  • 覆盖 getPreferredSize() 是在告诉布局"我需要 200×100"；pack 才会采纳它。没有首选尺寸的组件默认可能小到看不见。

--check 只证明"绘制方法被执行过"，不证明字的位置好看、颜色正确、窗口真的显示出来了。离屏检查与真实显示是两种证据，不能互相替代。

只改一处的实验：把 "Study" 改成 "Java"，--check 仍只输出 painted=true；所以还要真实启动看画面。再试一次：在 paintComponent 里写 painted = !painted，观察重绘次数不可控——不要在绘制方法里改业务状态。

独立小任务：把要显示的文字存进字段，加一个方法修改字段并调用 repaint()；启动后用窗口遮挡再露出，确认画面按新状态恢复，而不是回到旧文字。

8. 综合：FirstStudyFrame的两条运行路线

把前面的东西合起来：内容工厂负责造面板，EDT 负责显示，关闭策略负责退出。程序保留两条诊断路线，方便你在没有图形环境时也能验证一部分行为。

import java.awt.BorderLayout;
import java.awt.Dimension;
import java.awt.EventQueue;
import javax.swing.JFrame;
import javax.swing.JLabel;
import javax.swing.JPanel;
import javax.swing.SwingConstants;
public class FirstStudyFrame {
    static JPanel createContent() {
        JPanel panel = new JPanel(new BorderLayout());
        panel.add(new JLabel("讲义先学，教材深化。", SwingConstants.CENTER), BorderLayout.CENTER);
        panel.setPreferredSize(new Dimension(320, 180));
        return panel;
    }
    public static void main(String[] args) throws Exception {
        boolean check = args.length > 0 && args[0].equals("--check");
        boolean windowCheck = args.length > 0 && args[0].equals("--window-check");
        if (check) {
            EventQueue.invokeAndWait(() -> {
                JPanel panel = createContent();
                System.out.println("edt=" + EventQueue.isDispatchThread());
                System.out.println("components=" + panel.getComponentCount());
                Dimension size = panel.getPreferredSize();
                System.out.println("preferred=" + size.width + "x" + size.height);
            });
        } else {
            EventQueue.invokeLater(() -> {
                JFrame frame = new JFrame("Java学习台");
                frame.setDefaultCloseOperation(JFrame.EXIT_ON_CLOSE);
                frame.add(createContent()); frame.pack();
                frame.setLocationByPlatform(true); frame.setVisible(true);
                if (windowCheck) { System.out.println("showing=" + frame.isShowing()); frame.dispose(); }
            });
        }
    }
}

--check 输出 edt=true、components=1、preferred=320x180：它证明内容在 EDT 里构造、组件数和首选尺寸正确，不证明窗口显示。--window-check 会真的建立、显示、立刻释放窗口并打印 showing=true，适合本机快速冒烟；无参数运行才是你日常看到的样子。

运行方式 实际做了什么 能证明什么 不能证明什么
无参数 显示窗口，等你关闭 窗口可见、可交互 无（就是真实现场）
--check 只造面板，不建窗口 组件构造、数量、首选尺寸 窗口是否显示、布局是否好看
--window-check 显示后立刻释放 窗口能创建并显示 用户操作、长期稳定性

注意 JLabel 构造器里的 SwingConstants.CENTER 是水平对齐，不是"把标签放在窗口中间"；标签铺满 CENTER 区之后，文字在标签内部居中。这两个"居中"经常被混为一谈。

只改一处的实验：把标题改成“我的学习台”，--check 三行不变（标题不在检查项里）；所以标题是否生效只能靠真实窗口验证。再把首选尺寸改 400×220，--check 第三行应变成 400x220。

独立小任务：给窗口加一行状态标签，放在 SOUTH 区，显示“就绪”；要求内容工厂里完成这件事，main 不直接碰标签。完成后说明为什么这样分层更利于以后换成别的界面。

9. 运行与排错

所有命令都在课程根目录 PowerShell 输入。单文件程序用 java.ps1；复制到本课 my_code/ 后再改，把命令里的 code 换成 my_code。源码文件名必须与 public 类名一致。脚本在独立临时目录编译，编译失败不会拿旧 class 运行。

现象 先查哪里
窗口完全没出现 有没有 setVisible(true)；invokeLater 里的代码是否抛了异常
窗口很小或几乎空白 是否 pack()；内容有没有 getPreferredSize/setPreferredSize
关了窗口进程还在 关闭策略是不是 HIDE_ON_CLOSE/DO_NOTHING_ON_CLOSE；有没有别的非守护线程
命令一直不回提示符 窗口还开着，这是正常现象，不是卡死
内容被裁掉一截 用了 setSize 但内容首选尺寸更大；改成 pack 或调大尺寸
拖动后画面花掉 绘制是否依赖一次性状态；是否漏了 super.paintComponent
点按钮没反应、窗口“未响应” 是否有耗时循环/sleep 跑在 EDT 上
报 HeadlessException 当前环境没有图形显示；--check 只能做部分检查
中文显示为乱码 源文件保存为 UTF-8；命令行编译是否带 -encoding UTF-8

最后用一句完整的话回答本课：Swing 程序把界面对象交给事件分派线程，JFrame 只是外壳，组件放进内容窗格，pack 按首选尺寸定窗口，绘制由 paintComponent 回调完成，main 返回不影响仍在工作的界面线程。不要把这句话缩成“Java 窗口就是 JFrame”。
