学完要能做什么

能把竞争拆成读/算/写；用同一锁保护完整检查与修改及读取；解释条件等待释放/重获锁、while复查、通知与数据的区别；区分可见性、原子性、final引用、线程局部与死锁风险。

两个人各加一，结果为什么只有一

count++不是一句不可分的魔法。它有读旧值、计算新值、写回三个逻辑步骤；两人都读到0，再各写1，就覆盖了一次更新。像两人拿同一库存表各复印一张，都在自己的纸上把0改1，最后先后覆盖原表；类比边界是实际CPU/编译器还有可见性和重排规则，纸面交错只是能解释的一类竞争，不能覆盖整个内存模型。

import java.util.concurrent.CountDownLatch;
public class LostUpdateSchedule {
    public static void main(String[] args) throws InterruptedException {
        int[] count = {0}; CountDownLatch bothRead = new CountDownLatch(2);
        Runnable increment = () -> {
            int old = count[0]; bothRead.countDown();
            try { bothRead.await(); count[0] = old + 1; } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        };
        Thread a = new Thread(increment), b = new Thread(increment); a.start(); b.start(); a.join(); b.join(); System.out.println("count=" + count[0]);
    }
}

门闩bothRead让两线程都先读到旧0才继续写，join后输出count=1。这是有意安排出一种合法交错，不是靠循环百万次碰运气；它证明读/算/写组合会丢更新，不代表真实竞争每次都必然得1。门闩只安排了本例的阶段，没有把后面的写自动变成一个原子加一。

阶段 A的局部old B的局部old 共享count
A读 0 尚无 0
B读 0 0 0
门闩打开后A写 0 0 1
B写（也可反过来） 0 0 1

只把写回移到countDown之前，会破坏“双方先读后写”的安排，结果不再固定；独立任务：不用线程，手工模拟两份old和两次写回，把丢失发生在哪一步讲清，再做锁版本。把count声明volatile也不会把这三个步骤合成一个操作。

锁保护的是共同遵守的协议，不是给变量贴标签

临界区是一组必须作为整体互斥进行的操作；锁像唯一钥匙，所有相关读写者都用同一把，持有时才能检查/改变共享状态。类比边界是锁不会自动检查你绕路访问字段，也不会因字段private就给所有方法加锁。synchronized(lock)锁的是引用指向的对象，不是变量名字；两个不同new Object不是一把锁，同名字段也不相同。

实例synchronized方法使用this监视器，static synchronized使用该Class对象；二者不是天然同一把。离开同步块（含异常退出）自动释放监视器；Thread.sleep不释放已持有的监视器。持锁时可以被调度器换下CPU，互斥不是禁止线程切换，只是其他遵守同一锁的线程不能进入这段临界区。

可见性是另一个职责：释放同一锁与后续成功取得它建立相应可见性约定。把检查余额放在锁外、只锁最后写入，或者写加锁而读不加锁，都可能仍违反业务规则。锁也不会自动回滚半完成更新，必须先验证可能失败的条件再修改，涉及外部I/O更要设计失败恢复。

完整的同步计数：不要把错误门闩也搬进临界区

public class SynchronizedCounter {
    static class Counter { private int count; synchronized void add() { count++; } synchronized int get() { return count; } }
    public static void main(String[] args) throws InterruptedException {
        Counter c = new Counter(); Runnable task = () -> { for (int i = 0; i < 1000; i++) c.add(); };
        Thread a = new Thread(task), b = new Thread(task); a.start(); b.start(); a.join(); b.join(); System.out.println(c.get());
    }
}

输出2000。Counter被两个Runnable共享，add/get都使用同一this监视器，run中的i各是自己的局部循环计数。不要给本例add里硬塞前例bothRead.await：第一个人拿着锁等第二人，第二人却拿不到锁到达门闩，会人为造成挂起。

只把Counter c移到每个任务里new，两个各自1000不是一个共享2000；独立任务用private final Object gate替代方法synchronized，对同样完整主体加同步块，读写都使用gate。

显式锁：检查与两次修改必须是一个整体

import java.util.concurrent.locks.ReentrantLock;
public class LockedCredits {
    static class Ledger {
        private final long[] credits = {1000, 1000}; private final ReentrantLock lock = new ReentrantLock();
        boolean transfer(int from, int to, long amount) {
            if (from < 0 || from >= credits.length || to < 0 || to >= credits.length || amount < 0) throw new IllegalArgumentException("bad transfer");
            lock.lock(); try { if (credits[from] < amount) return false; credits[from] -= amount; credits[to] += amount; return true; } finally { lock.unlock(); }
        }
        long total() { lock.lock(); try { long sum = 0; for (long n : credits) sum += n; return sum; } finally { lock.unlock(); } }
    }
    public static void main(String[] args) throws InterruptedException {
        Ledger ledger = new Ledger(); Thread a = new Thread(() -> { for (int i = 0; i < 1000; i++) ledger.transfer(0, 1, 1); });
        Thread b = new Thread(() -> { for (int i = 0; i < 1000; i++) ledger.transfer(1, 0, 1); }); a.start(); b.start(); a.join(); b.join();
        System.out.println(ledger.total()); System.out.println(ledger.transfer(0, 1, 0));
        try { ledger.transfer(0, 1, -1); } catch (IllegalArgumentException e) { System.out.println("negative-rejected"); }
    }
}

这是整数额度模型，单位为教学积分，不是实际银行系统。transfer先拒绝负值并在锁内查余额，成功才扣/加；total同锁读取，输出2000、true、negative-rejected。可重入指同一线程已持锁后可再次取得，每次成功lock都对应unlock；finally释放并不自动恢复业务数据，所以先验证再修改很重要。

只把余额检查移到lock前，指出检查后到真正扣除间可能被别人改变；独立任务增加getBalance并使用同一锁。教材示例“锁保证不会被调度中断”要理解成临界区互斥，不是持锁线程永远占CPU。公平锁偏向等待者但不保证操作系统公平，性能也需测量；不要把公平当作正确性的替代。

条件对象：等待的是状态变得可做，不是等一声铃

单槽盒子一次只存一个整数。锁管同一时刻谁能检查/修改；changed管条件不满足时的等待集合。await必须持有关联锁，它会释放该锁等待，返回前再取得；signalAll仍在持锁区发出，不意味着接收方立刻插进来。

import java.util.concurrent.locks.*;
public class ConditionMailbox {
    static class Box {
        private final ReentrantLock lock = new ReentrantLock(); private final Condition changed = lock.newCondition();
        private Integer value; private boolean closed;
        void put(Integer item) throws InterruptedException {
            if (item == null) throw new IllegalArgumentException("null item"); lock.lockInterruptibly();
            try { while (value != null && !closed) changed.await(); if (closed) throw new IllegalStateException("closed"); value = item; changed.signalAll(); } finally { lock.unlock(); }
        }
        Integer take() throws InterruptedException {
            lock.lockInterruptibly(); try { while (value == null && !closed) changed.await(); Integer item = value; value = null; changed.signalAll(); return item; } finally { lock.unlock(); }
        }
        void close() { lock.lock(); try { closed = true; changed.signalAll(); } finally { lock.unlock(); } }
    }
    public static void main(String[] args) throws InterruptedException {
        Box box = new Box(); int[] sum = {0};
        Thread consumer = new Thread(() -> { try { Integer n; while ((n = box.take()) != null) sum[0] += n; } catch (InterruptedException e) { Thread.currentThread().interrupt(); } });
        Thread producer = new Thread(() -> { try { box.put(1); box.put(2); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } finally { box.close(); } });
        consumer.start(); producer.start(); producer.join(); consumer.join(); System.out.println("sum=" + sum[0]);
        Box empty = new Box(); empty.close(); System.out.println("closed=" + (empty.take() == null));
    }
}
状态 put take
空、未关闭 写值并通知 等待
满、未关闭 等待 取走并通知
关闭且满 拒绝 取剩余值
关闭且空 拒绝 null结束

两个worker结束后输出sum=3；另一个预先关闭的空盒取null。close不靠插一个与业务值混淆的整数作为结束；null业务消息明确禁止。while应对虚假唤醒以及别的消费者先取走条件。只把while改if，在当前小测试可能仍成功，这不能证明改法安全；独立任务写出两消费者被通知、第一人取走、第二人重获锁时空盒的反例。

更常见的生产者/消费者应优先用下一课BlockingQueue，本例是为了读懂教材底层规则。中断在方法上throws，由任务边界恢复退出；有多条失败路线的真实流水线还需要统一关闭，不能让生产者失败后消费者永久等待。

内部监视器：wait与notifyAll一定对同一对象说

public class MonitorOneShot {
    static class Result {
        private boolean ready; private String text;
        synchronized void set(String value) { text = value; ready = true; notifyAll(); }
        synchronized String get() throws InterruptedException { while (!ready) wait(); return text; }
    }
    public static void main(String[] args) throws InterruptedException {
        Result result = new Result(); Thread producer = new Thread(() -> result.set("数组")); producer.start();
        System.out.println("ready:" + result.get()); producer.join();
    }
}

输出ready:数组。get的while与set同用this监视器，wait释放this，让set有机会进入；即使set先执行，get先查ready会直接通过，不丢“早来的通知”。保存的是ready状态和text，通知本身不是可以日后领取的一张票。

只把ready检查删掉直接wait，若set早已完成就可能永远等不到新通知；不要把这种错误版作为正常测试长挂。独立任务给出先生产/先消费两条路线。Object.wait可用于已持有该监视器的同步块，不是只能在带synchronized修饰的方法里；教材p656 / PDF p674的简化应按监视器持有条件理解。

volatile发布与final：解决了哪一层

import java.util.ArrayList;
import java.util.List;
public class VolatilePublishOnce {
    static class State { int answer; volatile boolean ready; }
    public static void main(String[] args) throws InterruptedException {
        State state = new State(); Thread writer = new Thread(() -> { state.answer = 42; state.ready = true; }); writer.start();
        while (!state.ready) Thread.yield(); System.out.println(state.answer); writer.join();
        final List<String> names = new ArrayList<>(); names.add("数组"); System.out.println("size=" + names.size());
    }
}

writer先写answer再写volatile ready；读者看到ready后读取answer=42。这里循环只是短小发布实验，真实任务通常选门闩/Future等待，避免持续耗CPU。把ready去掉volatile后，即使本机这次仍成功，也失去这套发布保证；不把错误版预期写成“必然死循环”。

final引用列表仍可add，输出size=1；“引用不可重绑”和“对象不可变”是两件事。final初始化安全还要求正确构造、构造期间不把this泄漏给别的线程，不应把教材p659 / PDF p677理解成所有带final对象以后都能裸读写。

独立任务：把两个相关数作为不可变Snapshot对象，再通过一个volatile引用整体发布；先讲清为什么分别volatile两个数依然不保证二者构成同一时刻的快照。

ThreadLocal：同一个变量入口，每条线程拿到不同值

import java.util.*;
public class LocalTaskNotes {
    static final ThreadLocal<List<String>> notes = ThreadLocal.withInitial(ArrayList::new);
    static void work(String name, String[] result, int index) {
        try { notes.get().add(name); result[index] = notes.get().get(0); } finally { notes.remove(); }
    }
    public static void main(String[] args) throws InterruptedException {
        String[] result = new String[2]; Thread a = new Thread(() -> work("A", result, 0)), b = new Thread(() -> work("B", result, 1));
        a.start(); b.start(); a.join(); b.join(); System.out.println(result[0]); System.out.println(result[1]);
        try { System.out.println("main-size=" + notes.get().size()); } finally { notes.remove(); }
    }
}

输出A、B、main-size=0。ThreadLocal本身只有一个对象，get按当前线程取得那条线程自己的列表；withInitial收到创建列表的Supplier，首次get才执行。finally.remove清掉当前线程关联，防止线程池复用时下个任务读到上轮数据；不等同销毁ThreadLocal这个全局入口。

只把withInitial(() -> new ArrayList<>())改成返回同一个外部共享列表，会重新引入共享风险；独立任务解释为什么ThreadLocal不能把你故意共享的同一实例变成自动深复制。教材p664 / PDF p682的初始化方法正式名是initialValue，不是initialize，当前API写法按ThreadLocal文档。

超时锁与死锁：能退出等待，不等于业务自动重试正确

import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;
public class TimedLockAttempt {
    public static void main(String[] args) throws InterruptedException {
        ReentrantLock lock = new ReentrantLock(); lock.lock();
        try {
            Thread worker = new Thread(() -> {
                boolean got = false;
                try { got = lock.tryLock(1, TimeUnit.MILLISECONDS); System.out.println("acquired=" + got); }
                catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                finally { if (got) lock.unlock(); }
            }); worker.start(); worker.join();
        } finally { lock.unlock(); }
    }
}

main持有锁直到worker结束；worker只尝试1毫秒，失败返回false，不永久等，所以输出acquired=false。finally只在got为true时unlock；未取得锁却unlock会是另一种错误。1毫秒是等待上限请求，不是精确CPU调度承诺；不检查真实耗时必须恰好1ms。

lock不可中断等待，lockInterruptibly可响应中断，计时tryLock也可中断；成功后在finally释放。tryLock()可能不遵守公平排队，公平锁也不能保证调度器公平。超时让调用者有失败选择，不自动为你处理丢失任务或重试幂等。

死锁可能是A持锁1等2、B持锁2等1，也可能所有账户都在等永远没人能增加的余额；“用了锁”不保证活性。统一锁顺序、减少持锁期间外部调用、设定可取消等待并规定失败处理，分别解决不同来源。参考答案提供固定顺序程序，不故意让机器留下永久互锁线程。Windows诊断用本地JDK的jcmd或jconsole查看目标Java进程；书里的Ctrl+反斜杠不是PowerShell通用操作。

旧stop/suspend/resume不作为解决方案；在JDK21上相关方法已无法按旧书行为使用，见移除/变化说明。请求取消并在安全边界处理比外部强行中止更能维护状态一致性。

读写锁：多个读者可以共存，返回值仍要守住封装

import java.util.*;
import java.util.concurrent.locks.*;
public class ReadWriteCatalog {
    static class Catalog {
        private final List<String> names = new ArrayList<>(); private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();
        void add(String name) { lock.writeLock().lock(); try { names.add(name); } finally { lock.writeLock().unlock(); } }
        List<String> snapshot() { lock.readLock().lock(); try { return new ArrayList<>(names); } finally { lock.readLock().unlock(); } }
    }
    public static void main(String[] args) throws InterruptedException {
        Catalog c = new Catalog(); c.add("数组"); c.snapshot().clear(); int[] sizes = new int[2];
        Thread a = new Thread(() -> sizes[0] = c.snapshot().size()), b = new Thread(() -> sizes[1] = c.snapshot().size());
        a.start(); b.start(); a.join(); b.join(); System.out.println(sizes[0] + ":" + sizes[1]);
    }
}

写入用writeLock，快照用readLock并new ArrayList拷贝。main改返回副本不改变内部，再由两线程读，输出1:1。readLock不能用来保护修改；读者共存不等于同一可变对象能任意读写。不要持读锁后直接请求升级写锁，本课不设计这种可能挂起的协议。

只把snapshot返回值改为names引用，即使方法里加锁，调用者拿到后仍可在锁外clear内部列表。独立任务新增size也遵守读锁；说明“方法线程安全”与“暴露内部状态后整个类仍安全”之间的差别。此例只验证安全操作关系，不以小样例宣称性能提高。

在课程根目录PowerShell运行./java.ps1 -Source './L51_第14章C_共享状态锁与条件/code/ReadWriteCatalog.java'。
