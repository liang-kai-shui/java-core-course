## 0. 只把主程序装进箱子，为什么到另一台电脑就坏了

你的主类调用了别人写的LabelMaker，又需要一行放在message.txt里的文字。它们一个提供可执行的类，一个提供数据；两者都不是多写一个import就会自动出现。

本课把程序拆成三个角色：**应用类负责流程，库类提供能力，资源文件提供随程序分发的数据。** 先解释每项归属，再编译、打包、离开原目录运行。这样能检验它是否偷偷依赖开发目录里的文件。

## 1. 一张职责地图：相似的文件夹名称不等于相同规则

```text
project/
├─ src/campus/app/LibraryApp.java       应用源码
├─ library-src/campus/lib/LabelMaker.java  演示“别人提供”的库源码
└─ resources/campus/app/message.txt    应用资源，UTF-8文本

构建后：
release/
├─ app.jar                            应用class + message.txt + 清单
└─ lib/
   └─ labels.jar                      库class
```

这里library-src只是为了让你看到库的来历；实际使用第三方库可能只拿到JAR，而不在当前项目维护其源码。`src`、`resources`、`lib`是本项目的目录约定，名字本身不会触发下载、编译或加载动作。

把库JAR想成另一个供应方的部件箱，资源像本产品随箱附的文字说明。类比边界：真正加载时仍按类路径、资源路径和清单规则查找，不因为文件夹恰好叫lib就自动找到所有依赖。

## 2. 两份完整源码和一个数据文件

先把本课code/project复制到my_code/project，已有副本不覆盖。库只提供一个静态文本操作：

<!-- source: code/project/library-src/campus/lib/LabelMaker.java -->
```java-source
package campus.lib;

public class LabelMaker {
    public static String decorate(String text) {
        return "[" + text + "]";
    }
}
```

应用负责找到资源、读一行、交给库处理并输出：

<!-- source: code/project/src/campus/app/LibraryApp.java -->
```java-source
package campus.app;

import campus.lib.LabelMaker;
import java.io.InputStream;
import java.util.Scanner;

public class LibraryApp {
    public static void main(String[] args) {
        InputStream stream = LibraryApp.class.getResourceAsStream("/campus/app/message.txt");
        if (stream == null) {
            throw new IllegalStateException("missing resource");
        }
        try (Scanner in = new Scanner(stream, "UTF-8")) {
            String text = in.nextLine();
            System.out.println(LabelMaker.decorate(text));
        }
    }
}
```

resources/campus/app/message.txt的第一行是：

```text
讲义先学，教材深化。
```

末尾保留换行，以UTF-8保存。此程序约定资源存在且至少有一行；没有内容的文件与含一行空文本不同，Scanner读不存在的下一行会失败。先用明确存在的一行做主实验。

## 3. 先把新语法翻译成这一次能用的读法

**InputStream**表示字节输入流；这里是JAR里资源条目提供的读取通道。不是另一个字符串，也不是当前磁盘路径。

**`LibraryApp.class`**在Java源码中是类字面量，得到表示LibraryApp类型的Class对象，借它请求关联资源。**它与磁盘上同名的LibraryApp.class字节码文件不是同一语法角色**：前者是源码表达式，后者是文件名。不是对文件名直接调用方法，也没有打开一个以“class”命名的目录。

`getResourceAsStream(...)`找到资源后返回可读流，找不到返回null。因此先检查；`throw new IllegalStateException(...)`表示主动报告运行失败并停止正常路线，帮助把“找不到资源”与后续读取问题分开。异常体系留到对应章节，这里已给出可用读法，不要求先学完整继承结构。

`try (Scanner ... ) { ... }`为读取工具建立资源使用范围，退出时自动关闭它；它不是“出错了就假装成功”。Scanner的close也会关闭其输入流。L06先学习文件正常读写，这里用已经解释的资源语法避免忘关。

## 4. 资源路径从哪里开始，与note.txt的工作目录不同

本例以`/`开头，表示相对于类路径或归档内部的根：

```text
app.jar
└─ campus/app/message.txt  ← "/campus/app/message.txt"定位这里
```

它不是Windows的C盘根目录，也不自动加上src/resources。**构建要把resources里的内容复制到正确条目位置**，而不是把resources这个外壳一起塞进根。

如果写成`LibraryApp.class.getResourceAsStream("message.txt")`，没有前导斜杠，则相对于LibraryApp所属包定位；本例仍会得到campus/app/message.txt。两种写法起点不同，结果碰巧相同；换到别的包时需重新计算。

| 代码或命令中的路径 | 起点与职责 |
|---|---|
| Paths.get("note.txt") | 普通文件路径，通常从进程工作目录解释 |
| 类资源名 /campus/app/message.txt | 应用资源根，可能在JAR内部 |
| -cp classes;lib/labels.jar | 查找类的入口清单 |
| 清单Class-Path: lib/labels.jar | 按归档清单规则相对主JAR定位依赖 |

资源名使用`/`，不按Windows路径去写反斜杠。JAR中的资源也不一定对应能用普通文件工具打开的独立磁盘文件，因此先用流读取，不把资源URL随手硬转成本地文件路径。

## 5. 运行与打包：让工具执行完整链路

在课程根目录的PowerShell运行自己的副本：

```powershell
.\project.ps1 -Project S06 -SourceRoot '.\S06_结构基础_依赖与资源\my_code\project' -Mode Run
.\project.ps1 -Project S06 -SourceRoot '.\S06_结构基础_依赖与资源\my_code\project' -Mode Jar
```

两次都应显示`[讲义先学，教材深化。]`。Build模式会打印生成位置，List模式列出应用JAR内部条目。新生成目录位于课程.build，不混入自己的源码；失败时停止，不启动旧JAR。

工具实际完成：

| 顺序 | 输入 | 产物或用途 |
|---|---|---|
| 1 | library-src下LabelMaker.java | 编译为库class |
| 2 | 库class | 打包lib/labels.jar |
| 3 | 应用源码，加库JAR作为编译classpath | 生成LibraryApp.class |
| 4 | 应用class与resources内容 | 打包app.jar，并写入口、依赖位置 |
| 5 | app.jar与lib/labels.jar这一组 | 从新目录启动验证 |

这不是把库“复制到import那一行”。**编译时**需要能解析库类型，**运行时**需要能加载库类型；两阶段都要提供适当的类路径。

## 6. 手动观察两种classpath与清单条目

本段展示构建目录里的命令形状，**是路径读法示例，不是直接复制的完整命令**：

```text
javac --release 8 -cp "某次构建/lib/labels.jar" -d "某次构建/classes" 应用源文件路径
java -cp "某次构建/classes;某次构建/lib/labels.jar" campus.app.LibraryApp
```

Windows的多个classpath入口用分号连接，并把整段放在引号中，否则PowerShell可能把分号当自己的命令分隔符。Linux/macOS通常用冒号；不要把Windows这条命令原封不动当作所有系统的语法。

classpath指向库JAR本身，不是只写它所在的lib目录。`lib/*`可以在类路径规则下代表该层JAR集合，但不会递归收集所有源码和子文件夹；第一遍先明确列每一个需要的JAR。

应用JAR的清单包含：

```text
Manifest-Version: 1.0
Main-Class: campus.app.LibraryApp
Class-Path: lib/labels.jar
```

Main-Class选入口，Class-Path告诉这份归档还用哪个库。这里不是Windows-cp那样的分号清单；多个清单依赖条目按清单规范用空格分隔。本例只有一个相对项。

**`java -jar`不会把另写的普通-cp当作补充应用类路径来使用。** 本课为JAR启动明确写清单Class-Path；另一种做法是不用-jar，直接-cp提供完整集合并给主类。不要混用两种启动约定以后靠运气成功。

## 7. 发出去的一份程序，为何可能有多个JAR

本例是分开分发依赖的应用：app.jar没有把labels.jar里的类展开合并，lib/labels.jar仍需随它一起交付。

把Build生成目录中的**app.jar与lib子目录**复制到一个新建的实验文件夹。在那个新位置的PowerShell，用本机java工具完整路径执行`java -jar .\app.jar`；应有相同输出。实际命令用自己的JDK路径，不要指向开发期的classes目录。

如果只复制app.jar，预期执行到调用LabelMaker时报告依赖类缺失；此时入口可能已经加载，不能笼统说“没有main”。如果资源条目遗漏，程序会明确报告missing resource，这又与缺库不同。

某些工具能生成将依赖合并的所谓fat/uber JAR，但**普通jar打包不自动合并所有第三方库，也不自动把JVM装进去**。本课先用可以展开检查的分发目录理解真实需求。

## 8. 源码、资源、构建结果，哪些该改

改源码或资源后要重新编译/打包，再测试新产物。只改src里的文字，旧app.jar不自动更新。个人代码和实验放my_code；code保留原件；.build是可再生结果。

以后看到Maven的pom.xml或Gradle构建文件，先理解它们会描述依赖、版本、源目录与构建任务，不是另一种类定义。依赖标识、包名、JAR文件名也不一定彼此相同。这里先不要求安装构建系统，避免新的工具遮住已经能理解的class与JAR链路。

## 9. 本课过关

独立说明“缺入口、缺库、缺资源、运行旧产物”分别应查哪一处。能在离开源码目录以后运行这一组分发文件；能解释资源的查找起点，区分源码中的.class表达式与磁盘字节码文件名。做到这些，再去学更大的框架，才不必把整个项目当作一个神秘按钮。
