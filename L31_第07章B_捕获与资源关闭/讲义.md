## 困惑：捕获异常后，资源为什么还是忘了关

try/catch负责转到处理失败的路线；它本身没有规定关资源。**finally**是离开相关try结构时要执行的收尾路径；**try-with-resources**专门为声明的AutoCloseable资源安排close。像借了两把钥匙，办事成功失败都应交还，最后借的先还。边界是close是否真正释放正确资源由类实现负责，语法不能替一个空close完成操作；JVM被强制终止、System.exit等也不能保证普通finally继续运行。

本课用可打印的模拟资源，目的是看清语言关闭顺序与异常保留，不声称它测试了磁盘设备。main先走全部成功，再走工作与关闭都失败。

```java
import java.io.IOException;
public class ResourceExitRoutes {
    static void use(boolean failBody, boolean failClose) {
        try (TraceResource a = new TraceResource("A", false);
             TraceResource b = new TraceResource("B", failClose)) {
            a.use(); b.use();
            System.out.println("work");
            if (failBody) throw new IOException("body");
        } catch (IOException ex) {
            System.out.println("caught:" + ex.getMessage() + " suppressed=" + ex.getSuppressed().length);
        } finally {
            System.out.println("finally");
        }
        System.out.println("continue");
    }
    public static void main(String[] args) {
        use(false, false);
        System.out.println("---");
        use(true, true);
    }
}
class TraceResource implements AutoCloseable {
    private final String name;
    private final boolean failClose;
    private boolean closed;
    TraceResource(String name, boolean failClose) {
        this.name = name; this.failClose = failClose;
        System.out.println("open:" + name);
    }
    void use() { if (closed) throw new IllegalStateException("closed resource"); }
    @Override public void close() throws IOException {
        closed = true;
        System.out.println("close:" + name);
        if (failClose) throw new IOException("close-" + name);
    }
}
```

预期输出：

```text
open:A
open:B
work
close:B
close:A
finally
continue
---
open:A
open:B
work
close:B
close:A
caught:body suppressed=1
finally
continue
```

`try (TraceResource a=...; TraceResource b=...)`按从左到右初始化资源；两者都成功才进入块。离开时逆序先b.close后a.close。close中即使B抛出IOException，仍会尝试关A。资源变量范围在try结构中受限，不能在后面随便继续使用已经关闭的资源。

块中的a.use()/b.use()代表对两个已打开资源做操作；use检查closed标志，若已关则拒绝。本轮进入块时两者都未关，因此不另打印内容；close把标志置true。它展示使用与关闭是同一实例的状态变化。

| 路线 | 工作结果 | 关闭B | 关闭A | 外层收到 |
|---|---|---|---|---|
| use(false,false) | 成功 | 成功 | 成功 | 无异常，跳过catch |
| use(true,true) | body异常 | 又失败 | 成功 | 主异常body，关闭失败记suppressed |

`getSuppressed()`返回附带失败数组，长度1说明关闭时还有一个失败；它不是被“忘掉”的失败。若工作成功、只有关闭失败，关闭失败就成为主异常，不会神奇被全都吞掉。若第二个资源构造就失败，第一个已成功建立的资源仍要关闭，第二个没建立完不能当成功资源close。

## catch按类型，不按错误消息猜

有多个catch时，从前往后选第一个能接住实际异常类型的处理器，较具体类型放前，父类型在前会让后面的子类型处理器不可达并编译失败。一个catch可写`catch(A | B ex)`共用处理，其中A/B不能互为父子类型，变量不能被重新赋值。不要为了省事把所有东西catch(Throwable)然后继续假装成功，Error类严重故障通常不适合这类恢复。

正常try结束会跳过catch，再执行finally；匹配异常先catch再finally；未匹配异常仍执行finally后继续外传。catch里再次throw也仍经过finally。finally中不要return或抛一个无关新异常，否则可能覆盖原来的返回/失败。try-with-resources把工作失败与close失败的保留规则处理好了，优先于自己手写一堆脆弱finally嵌套。

注意`finally`、`final`、`finalize`完全不同：finally是控制流收尾，final约束赋值/覆盖/继承，finalize是L16已经说明不依赖的历史回收回调。

## 真正读取文本时，EOF不一定是异常

E2用BufferedReader包住StringReader，把一段内存文本当字符来源。readLine返回一行不带换行的String，到正常结尾返回null；`while((line=in.readLine())!=null)`先赋值再判断，每轮处理新的一行。空文本直接null，空行则是空字符串，不可混淆。EOFException只适用于某个协议还承诺有数据却提前结束等情境，不是所有“读到结尾”都抛异常。

`try(BufferedReader in=new BufferedReader(new StringReader(text)))`关闭外层reader时会连带关闭底层来源。本例不持有操作系统文件，但同样展示资源所有权；换成Files.newBufferedReader读文件，要给UTF-8与真实路径，文件环境失败仍可能IOException。关闭System.in会影响后续整轮键盘读取，资源由谁创建、谁还需要使用要先说清。

## 堆栈怎样帮你找到第一次出错的位置

printStackTrace通常写向System.err，首行类型和消息，后面at行从抛出附近向外到调用者；Caused by保留原因链，Suppressed保留额外关闭失败。getStackTrace可得到StackTraceElement数组，查询类名/方法名/文件/行号，行号可能不可用，不把具体行数写死为永久规则。日志记录完整异常对象比仅写getMessage更方便定位。线程全堆栈在L50再用，不为一个数组越界先分析所有JVM线程。

## 实验与独立任务

只把第二次调用use(true,true)改use(false,true)，观察主异常变close-B、suppressed为0；这能分清“工作先失败”和“关闭首先失败”。再单独改use(true,false)，只有body失败且suppressed0。每次预测完整关闭路线，不只看caught一行。

## return已经算出的值，finally还能改变哪一部分

finally执行前，普通return表达式已求出返回值，但方法尚需完成收尾。像先把结果填入回执，再去交还钥匙；边界是finally自己再return会覆盖原回执，所以正常代码避免在finally里返回。

```java
public class ReturnThroughFinally {
    static int calculate() {
        int value = 1;
        try {
            return value;
        } finally {
            value = 2;
            System.out.println("finally=" + value);
        }
    }
    public static void main(String[] args) {
        System.out.println("returned=" + calculate());
    }
}
```

try的return先取得int1；finally把局部value改2并打印，然后原返回值1交回main。不是finally完全无效，也不是局部变量改了就把已求值的返回结果重算。该结论针对这里的基本int；若返回可变对象引用，finally改对象内部又是另一种共享行为。

| 事件 | 局部value | 待返回int |
|---|---:|---:|
| return表达式求值 | 1 | 1 |
| finally修改 | 2 | 仍1 |
| main接结果 | 局部调用结束 | 1 |

只把finally打印文本改掉，不影响返回值；若在独立错误副本finally加入return2，会覆盖原返回并可能收到finally无法正常完成的编译警告，不能把它当正常推荐写法。独立任务：解释抛异常离开时finally也会先运行，但finally中抛新失败可能覆盖原原因；资源关闭优先使用前面try-with-resources保留suppressed的规则。
