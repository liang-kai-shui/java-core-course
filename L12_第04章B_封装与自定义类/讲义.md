# L12 讲义 · 封装：把数据规则放进自定义类

> 前置：S02、S03；L07条件分支
> 教材主线：4.3；**书本 p103–112 / PDF p121–130**。讲解、类比、案例与练习均为课程原创。

## 学完要能做什么

能从一条状态规则设计字段、构造器和公开操作；解释private的保护边界；避免把内部可变对象原样交出去。

## 困惑：把字段改成private，就自动安全了吗

你写借阅登记，规则是“在借数量不能为负，也不能超过上限”。如果任何地方都能写`count=-9`，每个调用者都要记住规则。**封装**就是把状态和维护它的操作组织在一起，让外部通过有意义的门办理业务。像图书室柜台：读者提出借/还请求，柜台核对后改变库存。类比边界是private不是安全沙箱或加密；它约束Java源代码的成员访问，不能防住被授权的反射或对原始存储的攻击。

只把字段设private，再加一个不检查的`setCount(int n)`，仍然敞开了破坏规则的门。先写清不变量：每个有效Borrower对象都满足`0 <= count <= limit`。构造完成时成立，每次公开操作后也必须成立。不变量是持续维护的状态规则，不是每个变量都要写final。

## 从零次借阅开始

```java
public class BorrowDesk {
    public static void main(String[] args) {
        Borrower reader = new Borrower("小林", 2);
        System.out.println(reader.summary());
        System.out.println(reader.borrow());
        System.out.println(reader.borrow());
        System.out.println(reader.borrow());
        System.out.println(reader.summary());
    }
}
class Borrower {
    private final String name;
    private final int limit;
    private int count;
    Borrower(String name, int limit) {
        this.name = name;
        this.limit = limit;
    }
    boolean borrow() {
        if (count == limit) return false;
        count++;
        return true;
    }
    String summary() { return name + ":" + count + "/" + limit; }
}
```

预期输出：`小林:0/2`、`true`、`true`、`false`、`小林:2/2`，各占一行。先别运行，自己在纸上扮演对象。

`Borrower`是本例的业务类，没有main；`BorrowDesk`负责启动和演示。它们为方便实验放在一个文件，只有BorrowDesk是public，文件叫BorrowDesk.java。正式多文件布局见S04。本例从“一个程序只能一个类”的误会中走出来：启动入口只有这里一个，不等于程序只允许一个类。

`private final String name`里的private规定外部不能直接访问；final规定这个字段构造后不再重新赋值。String本身也不可变，但final若修饰数组引用，只固定引用，不会冻结元素。`private int count`需要随借阅变化，因此不加final。构造器名称Borrower与类名相同，无返回类型；先把name、limit写入对象，count字段未显式赋值时为0。

`boolean borrow()`返回这次请求是否成功；`if(count==limit) return false`结束本次方法调用，后面的自增不会再执行。否则先增加再报告true。`summary()`只产生可读描述，没有把内部字段交给调用者写。

| 请求 | 进入前count | 判断 | 离开后count | 返回 |
|---|---:|---|---:|---|
| 第一次borrow | 0 | 还没满 | 1 | true |
| 第二次borrow | 1 | 还没满 | 2 | true |
| 第三次borrow | 2 | 等于上限 | 2 | false |

每次调用中的this都指向点号左边那个Borrower对象。第二个读者有自己的count，不能因为方法代码只有一份就把状态也共享了。代码共享与实例数据独立要分开理解。

## 参数合理性、可见性与可变字段的出口

本示例假设构造时传入非负上限。独立练习会要求明确处理负数；不能一边声称“不变量永远成立”一边允许负上限进入。这里可以先采用“负上限归零”的业务规则，异常方式留到L30后比较；没有放之四海皆准的静默修正策略。

方法内部可以访问另一个同类对象的private字段；private按类授权，不按单个实例授权。另一方面，返回内部可变数组会绕过边界：若`getScores()`直接返回内部scores，外部拿到引用就能改元素。防御性复制指返回副本，例如`scores.clone()`，让外部改副本不会动原数组。`LocalDate`不可变，返回它通常不需要这种复制；旧Date可变则要认真处理。

设计新类时先问“调用者要完成什么”，再选操作。借书是borrow，还书是giveBack；这比暴露无条件setCount更容易维持规则。类的职责也要单一：此处不让Borrower同时读取键盘、打印菜单和写文件，才能在无键盘输入时单独验证业务。

## 一处修改实验与独立小任务

先把main中上限2改为0，其他不动。应三次都返回false，数量一直0。若出现1/0，守门条件没有先于修改执行。再分别创建两位读者，只对第一位借书，预测第二位的数量。

独立实现returnOne：零本时返回false且保持0，否则减少1并返回true。写下从0还、借两本后还、再次还到0三个过程，验证规则既限制上边界也限制下边界。排错时先查改变字段的每条路径，而不是只盯最后的打印行。

## private守住变量名，为什么还要守住引用出口

如果外部拿到内部数组引用，就能改元素而无需访问private字段名。像柜台不让你改库存登记字段，却把仓库的同一把钥匙交给你；类比只说明共享访问路径，不代表Java引用真是可见的钥匙或地址。

```java
public class DefensiveScoreCopy {
    public static void main(String[] args) {
        int[] input = {70, 80};
        ScoreSnapshot scores = new ScoreSnapshot(input);
        input[0] = 1;
        int[] view = scores.snapshot();
        view[0] = 2;
        System.out.println("input=" + input[0]);
        System.out.println("view=" + view[0]);
        System.out.println("inside=" + scores.first());
    }
}
class ScoreSnapshot {
    private final int[] values;
    ScoreSnapshot(int[] values) { this.values = values.clone(); }
    int[] snapshot() { return values.clone(); }
    int first() { return values[0]; }
}
```

构造器的`values.clone()`在**入口**复制，防止调用者以后改输入数组影响内部。snapshot中的clone在**出口**复制，防止拿回快照的人改内部。clone在int[]上返回另一个int[]，复制元素值，不需额外写new；这里不是任意对象的深复制方案。

| 时刻 | input[0] | 对象内部第0项 | view[0] |
|---|---:|---:|---:|
| 构造后 | 70 | 70 | 未建立 |
| input[0]=1后 | 1 | 70 | 未建立 |
| 得快照并改为2后 | 1 | 70 | 2 |

只把构造器clone删去，先预测最终内部值会不会变1；恢复后只把snapshot的clone删去，预测会不会变2。两份实验分开保存，否则无法定位漏的是入口还是出口。独立任务：给原类增加size和scoreAt访问器，让调用者能读指定项而不能直接写内部数组；下标约定0到size-1，非法位置的失败要明确。防御性复制不要求所有类型都复制，LocalDate与String不可变时可以共享值。
