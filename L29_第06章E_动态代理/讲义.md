## 先手写同接口包装，再看动态工具省掉了什么

动态代理前先认识最普通的包装：外层也实现同一接口，内部保存真实对象，前后登记后转发。像前台自己明确写出每种业务的转交步骤；边界是这仍是本机普通调用，没有自动网络、线程或安全隔离。

```java
public class ManualProxyBeforeDynamic {
    public static void main(String[] args) {
        MessagePort view = new LoggedMessage(new RealMessage());
        System.out.println(view.send("数组"));
    }
}
interface MessagePort { String send(String text); }
class RealMessage implements MessagePort {
    public String send(String text) { return "sent:" + text; }
}
class LoggedMessage implements MessagePort {
    private final MessagePort target;
    LoggedMessage(MessagePort target) { this.target = target; }
    public String send(String text) {
        System.out.println("before");
        String result = target.send(text);
        System.out.println("after");
        return result;
    }
}
```

view指向LoggedMessage，target指向RealMessage，是两个对象。view.send进入包装器，打印before，调target.send得到字符串，再打印after，返回main才显示结果。该路线与本课动态Trace相同，但这里方法签名明确写在类中，无需Method.invoke或Object[]参数。

| 步骤 | 对象 | 输出/结果 |
|---|---|---|
| 接调用 | LoggedMessage | before |
| 转发业务 | RealMessage | 返回sent:数组 |
| 转发完成 | LoggedMessage | after |
| 返回显示 | main | sent:数组 |

只把main中的包装去掉而保留真实对象，结果仍sent:数组，但前后记录消失。独立任务：画同一张路线图，再把LoggedMessage的位置替换成“动态代理→处理器”，指出动态机制代为生成的是接口转接层，业务仍由真实对象完成。转发给自身会重入，不是让业务更快。

## 困惑：想记录每次调用，为何不修改所有业务类

你有一个“发送提醒”接口，希望在调用前后记录轨迹。可以手写一个同接口包装类，也可用JDK**动态代理**在运行时产生实现指定接口的类，再让统一处理器决定怎样处理调用。像前台接住客户请求，登记后转给承办者，再把结果交回。边界是代理并不自动完成真正业务，也不会凭空给对象添加任意类继承关系；JDK这种代理围绕接口工作。

本课为工具机制深化，基础应用先会普通接口即可。仍提供完整可追踪程序，不能仅背“代理底层用了反射”就认为理解。

```java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;
public class ProxyRoute {
    public interface NoticeService { String send(String text); }
    public static class RealNotice implements NoticeService {
        @Override public String send(String text) { return "sent:" + text; }
    }
    static class Trace implements InvocationHandler {
        private final NoticeService target;
        Trace(NoticeService target) { this.target = target; }
        @Override public Object invoke(Object proxy, Method method, Object[] arguments) throws Throwable {
            if (method.getDeclaringClass() == Object.class) {
                if (method.getName().equals("equals")) return proxy == arguments[0];
                if (method.getName().equals("hashCode")) return System.identityHashCode(proxy);
                if (method.getName().equals("toString")) return "NoticeProxy";
            }
            System.out.println("before:" + method.getName());
            try {
                Object result = method.invoke(target, arguments);
                System.out.println("after:" + method.getName());
                return result;
            } catch (InvocationTargetException ex) { throw ex.getCause(); }
        }
    }
    public static void main(String[] args) {
        NoticeService proxy = (NoticeService) Proxy.newProxyInstance(NoticeService.class.getClassLoader(),
            new Class<?>[] {NoticeService.class}, new Trace(new RealNotice()));
        System.out.println(proxy.send("复习"));
        System.out.println(proxy.equals(proxy));
        System.out.println(proxy);
    }
}
```

输出`before:send`、`after:send`、`sent:复习`、`true`、`NoticeProxy`。真实对象返回字符串，本例没有另打印“target”一行；不要把脑中执行步骤和实际println数量混为一谈。

接口NoticeService、真实类RealNotice和处理器Trace放在启动类中并标static，不需要创建ProxyRoute外围对象。NoticeService是public接口，RealNotice公开实现send。Trace保存target真实对象引用，与proxy生成对象是两个不同对象；反射转发必须调用target，若错误调用proxy会再次进入处理器，造成递归。

`Proxy.newProxyInstance`三项分别是：接口能被看到的类加载器、要实现的接口Class数组、处理器实例。用NoticeService.class.getClassLoader取得合适加载器，不把null误解成“当前应用的默认查找万能值”；null表示引导加载器相关选择，未必能看到你的应用接口。`new Class<?>[]{NoticeService.class}`这里是一个Class数组，不是源码文件目录。

| 步骤 | 当前接收者 | 行为 |
|---|---|---|
| proxy.send("复习") | 动态产生的代理实例 | 转到处理器invoke |
| invoke检查method | Trace | 本次是send，不是Object方法 |
| before打印 | Trace | 记录send |
| method.invoke(target,args) | RealNotice | 返回sent:复习 |
| after打印/return | Trace→代理→main | 结果交回 |
| println结果 | main | 打印sent:复习 |

## 三个参数别混：proxy、method、arguments

InvocationHandler.invoke的proxy是当前代理对象；method是本次方法描述；arguments是这次显式实参数组，无参调用可能是null。它不是直接把任意Java语句传进来，也不是参数已经变成字符串。invoke返回Object，接口要求的引用结果由代理交回；基本类型则要匹配相应包装值，否则可能在运行时失败。

`method.invoke(target,arguments)`又是一层反射调用，与处理器的invoke名字相同但职责不同：前者执行真实方法，后者是代理回调。真实方法若抛异常，反射会包装InvocationTargetException；本例catch这个包装后throw getCause，让原始原因继续沿代理契约传播。`throws Throwable`来自InvocationHandler契约，读作可以向外报告该层允许的失败，不是“把所有错误忽略”。若处理器抛了接口未声明的受检查异常，代理可能包装为UndeclaredThrowableException，L30再完整看层次。

## equals、hashCode、toString也可能经过代理

这三个Object方法也会进入处理器。本例显式规定：equals按代理身份`proxy==arguments[0]`；hashCode用System.identityHashCode(proxy)，与该身份规则一致；toString返回固定NoticeProxy。不要简单把equals转给target，否则proxy.equals(proxy)也可能不符合你期望的自反规则。不能在处理器日志里直接拼接proxy，拼接会触发toString，若未处理又记日志就可能再次递归。

getClass等Object方法不会像这三项一样全部转发。Proxy.isProxyClass(proxy.getClass())用于确认动态代理类；不要断言生成类永远叫$Proxy0、属于固定包，或依赖某个JDK的内部编号。教材代理类可见性/包描述有版本细节，本课只使用公开应用接口，不借它绕访问权限。

## 实验、排错与使用边界

只把“复习”改“数组”，前后轨迹不变，结果变sent:数组。再在副本将真实对象转发目标target误改proxy，预期运行递归直至失败，先从调用图解释，正常源码保持正确，不把故障长时间运行。若创建失败，先核对数组里的类型真是接口、加载器能看到它们；若结果类型失败，检查处理器返回值是否符合接口。

独立给ValueService.twice(int)做代理，真实实现返回x*2，本题x限定小整数。处理器只在业务调用前打印call:twice，再转发；Object方法按明确身份规则处理。测试0、3、-2，不假称这个转发是远程请求；若需求固定且只有一个接口，手写包装器通常更直观，动态机制为变化中的工具场景提供价值。
