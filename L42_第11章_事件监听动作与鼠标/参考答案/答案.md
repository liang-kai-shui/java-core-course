# L42 参考答案与解析

先独立完成，再比较推演。事件顺序、焦点行为与平台有关，判断看规则与实测记录，不要求与示例截图一致。

## Q1

| 角色 | 本课对应 | 职责 |
|---|---|---|
| 事件源 | `JButton` | 产生 ActionEvent，按注册表分发 |
| 事件对象 | `ActionEvent` | 携带 source、命令字符串、修饰键等 |
| 监听器 | Lambda / Counter / 匿名类 | 实现 `actionPerformed`，改模型 |
| 业务状态 | `count` | 真正的数据 |
| 显示 | `JLabel` | 从状态刷新，再由 EDT 重绘 |

注册（`addActionListener`）只是把对象记到按钮的监听器列表里，不会执行；执行发生在按钮产生事件并分发时。所以“我注册了监听器”不等于“动作已经跑过一遍”。

按钮的 `ActionEvent` 比直接监听鼠标覆盖更多激活方式：鼠标点击、键盘空格激活焦点按钮、菜单项、程序 `doClick`、`Timer` 到点都会产生 `ActionEvent`。如果你监听 `mouseClicked`，键盘用户和程序化触发就被漏掉了。

常见错法：把 `label.setText` 当成“立刻重绘”；把事件源和监听器混为一谈；说“注册时就执行了一次”。

## Q2

```text
按键 KeyStroke ──► InputMap：键 → 内部动作键 "course.add"
                              │
                              ▼
                    ActionMap：内部动作键 → Action 对象
                              │
                              ▼
                    actionPerformed → 改 count → refresh 标签
```

| 问题 | 参考回答 |
|---|---|
| 两张映射各存什么 | InputMap 存“按键→动作键”，ActionMap 存“动作键→Action” |
| 为什么要内部键 | 显示名会被翻译、会改；映射键要稳定，不能拿显示名当键 |
| Action 禁用 | 由它创建的按钮/菜单项变灰，入口被挡住 |
| 直接调用 actionPerformed | 绕过入口与 enabled 检查，仍然会执行；只适合测试内部逻辑 |
| 为什么还要 @Override | 适配器方法拼错时只是新增方法，编译器不报错；@Override 会让它报错 |
| closing 与 closed | closing 是“请求关闭”（还能取消），closed 是“已经关闭” |

`windowClosing` 里可以弹确认框、决定是否 `dispose`；`windowClosed` 时窗口已经没了，再拦也来不及。教材 p452 特意用 `windowIsClosing` 这个拼写错误举例，说明没有 `@Override` 时错误会静默通过。

## E1

参考记录：

```text
真实点击两次：标签 0 → 1 → 2
--check：count=2，label=2（doClick 触发，不是鼠标）
只改增量 +2：两次点击后 count=4，label=4
```

三个样本的证据范围：

| 样本 | 证明了什么 | 没证明什么 |
|---|---|---|
| SharedActionBinding | 一个 Action 同时接按钮与键映射，禁用同步 | 真实按键、焦点 |
| MouseModelRoute | 合成 MouseEvent 能改模型并 repaint | 真实鼠标轨迹、窗口焦点 |
| SwingTimerTicks | Timer 回调在 EDT、到点停止 | 毫秒级精度、真实等待时长 |

不能把三者合并成“鼠标测试通过”。合成事件、程序化点击、真实输入是三种不同证据。

## E2

参考实现见 [ResettableSteps.java](ResettableSteps.java)。状态序列：

| 操作 | count | 标签 |
|---|---:|---|
| 初始 | 0 | 0 |
| 加一 | 1 | 1 |
| 加一 | 2 | 2 |
| 重置 | 0 | 0 |
| 加一 | 1 | 1 |

`--check` 输出 `label=1`、`count=1`。经典错误是重置只写 `label.setText("0")` 而不改 `count`：界面看起来归零，下一次加一会从 3 开始，这个序列会立刻暴露它。

## E3

参考实现同一个 [ResettableSteps.java](ResettableSteps.java)：`add` 是 `AbstractAction`，`new JButton(add)` 创建按钮，`WHEN_IN_FOCUSED_WINDOW` 映射 `ctrl R → course.add`，`ActionMap` 把 `course.add` 指回 `add`。

`--check` 的顺序是：先从 InputMap 取键，再从 ActionMap 取动作，确认 `isEnabled()` 后触发，最后 `setEnabled(false)` 观察按钮变灰。直接调用 `actionPerformed` 只能验证“动作体本身”，不能证明键盘入口在真实焦点下可用。

真实快捷键测试要记录：窗口是否有焦点、绑定在哪张映射、按键字符串是否写对。禁用 Action 后“加一”按钮不可用，但“重置”按钮用的是独立监听器，仍然可用。

鼠标路线（按下/拖动/释放）改的是模型坐标，画面更新来自 `repaint()`；不要在鼠标回调里直接拿 Graphics 画。

## E4

参考实现见 [TwoListeners.java](TwoListeners.java)，输出 `count=2`、`source=true`：两个监听器都收到了两次点击，且 `getSource()` 都是同一个按钮。

但两个监听器的**执行顺序**不能依赖。`ListenerRegistrationOrder` 实测输出：

```text
third,second,first
third,second,first,third,first
```

后注册的先通知（Swing 的 EventListenerList 当前实现从尾部向前分发）。规范没有承诺顺序，换组件或换实现都可能不同。需要固定先后时，应在一个监听器里按顺序调用两个方法，而不是注册两个监听器赌顺序。

常见错法：用 `==` 比较事件对象；把 `getSource()` 当成监听器；用两个 Lambda 想移除其中一个（没有保存引用就移除不掉）。
